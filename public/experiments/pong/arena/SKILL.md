# Author literal network parameters

The author supplies every parameter. The operator defines the task, captures submissions and evaluates accepted networks. These roles can use different execution environments.

## Prepare the packet

Read the task contract before authoring. Verify observations, actions, architecture, activations, parameter order, arithmetic, ties, transitions, termination, schedule and failure policy. Keep task identities, dimensions, bounds, paths and spending permissions in the packet. The companion Pong packet includes its own contract and validator invocation.

Bundle the executable canonical validator, supported runtime, hashes and weight-free usage instructions. Exercise the packaged checker with valid input, wrong counts, malformed syntax, duplicate keys, excess bytes, out-of-range values and precision failures. Keep these fixtures and any solution weights outside the author's payload. Verify that the author can actually execute the checker. If only the operator can run it, declare that route.

Before each official run, freeze and hash the author-facing prompt independently from the kernel, validator, evaluator and ordered schedule. Declare the provider route, visible identity evidence, context, output allowance, deadline, attempt and correction budgets, and any spending authority. An assistant display name alone cannot establish an exact model identity.

## Declare the track

- **Unaided original.** Start a clean context with the frozen packet. Apply the declared tools-off and no-repair conditions. Exclude earlier submissions, demonstration weights, fixture weights, strategy solutions and gameplay results.
- **Validation-assisted original.** Declare the checker, who runs it, allowed diagnostic fields, maximum checks and stopping rule before submission. Return only permitted syntax, dimension, numeric-grammar and bounds diagnostics. Accept the first valid response within budget.
- **Feedback revision.** Freeze the original and its measured results first. Give the author their original player and the declared match feedback. Identify the parent by its parameter fingerprint and record exactly what feedback was shared. Declare a fresh budget and validation route. Ask for a complete revised artifact and a short account of the author's changes. Evaluate the revision under the declared schedule before reporting any improvement.

A mechanical adapter needs its own declared track. Specify the accepted shape, exact block sizes, fixed order and token-preserving transformation. Verify the derived bytes with the canonical validator. Keep raw and derived artifacts and hashes separately. The checker and adapter must never fill, pad, truncate, optimise, train or choose weights.

## Capture and validate

Preserve each response before transformation, including partial output, refusals, errors and late submissions. Preserve code fences and whitespace as received. Record identity evidence, visible settings, timestamps, usage when available and exact request and capture hashes. Distinguish captured UI text, clipboard text and transport bytes. Record unknowns.

Stay within the declared budget. For assisted rounds, pair each response with the exact diagnostics returned. Retain rejected attempts even when a later attempt succeeds.

Run bounded byte, lexical, duplicate-key, schema, dimension, finite-value and bounds checks before tensor allocation. A byte-limit rejection does not establish a scalar count. Keep original receipts immutable. Store supplemental validation reports, derived hashes and corrections in an outer index.

## Evaluate and hand off

Freeze acceptance before revealing gameplay. Run only the declared evaluator and schedule. Mark rejected or missing artifacts as unplayed. Record the accepted bytes, validator identity, parameter fingerprint, opponents, side assignments, outcomes and tie-breaks.

Report formatting success, playing strength and observed changes separately. State whether the observation came from live inference or a replay. Give the integrator allowlisted public facts and verified measurements. Keep private account details, raw prompts and receipts private unless their release is authorised.
