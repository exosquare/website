The wider question is whether a language model can write a tiny network as static numbers that play a genuinely new browser game, without calling the model during play. Pong is our first setting. It is familiar, and choosing it does not show that the game is new, or that a model has no prior knowledge of it.

Other researchers have asked models to write weights directly, under the name [weight-space programming](https://rikiyat.github.io/blog/weight-space-programming/). In one [number-edit experiment](https://github.com/RikiyaT/lm_understand-logs/blob/main/exp5_write_from_scratch/README.md), the authors supplied the rules, the exact game source, and the definitions of the observations, actions, network, and scoring. That work is useful motivation. It does not tell us that an exact source is required, or how much specification a model needs.

## How the player is put together

The player on this page is a small JavaScript program we wrote for this experiment. It does not use TensorFlow or PyTorch. If a language model writes a player, it does that beforehand, as a list of static numbers. During the game, this little program uses that fixed list locally. There is no training in play, and no live call to Grok.

Each step of play starts from the game state, meaning the current position and direction of the ball and the positions of both paddles. That state is turned into six inputs, each scaled into a small numeric range: the ball's horizontal and vertical position, its horizontal and vertical velocity, and the centres of both paddles. The six inputs pass through two hidden layers of 16 units each. A unit is a small step that combines incoming numbers into one result. Hidden just means those units sit between the inputs and the final scores. At the end there are three action scores, one for staying still, one for moving the paddle up, and one for moving it down. The paddle then follows the winning action.

A weight is a number on a connection from one unit to the next, and it multiplies the value coming in. A bias is an extra number for that unit, added after those products have been summed, which raises or lowers the total. In the hidden layers, a negative total becomes zero, and a positive total is left as it is. The three final scores are ordinary totals, not probabilities. After a fixed rounding step, the action with the highest score is used. If two rounded scores are equal, the earlier action wins, so stay beats up, and up beats down.

These 435 numbers are parameters, made of 400 connection weights and 35 biases, not 435 neurons. We chose this small shape so every number can sit on the page: (6 × 16) + 16 = 112 in the first hidden layer, (16 × 16) + 16 = 272 in the second, and (16 × 3) + 3 = 51 for the three action scores. Pong does not require this count. The demonstration can start a serve, pause, and step through play, so the ball and paddles move under the current numbers. On each tick, both paddles are decided from the state at the start of the tick, then the game rules move the paddles and the ball. The numbers stay fixed while that happens. This is not a recording of a game played earlier. After the required assets have loaded, play is intended to use those local numbers only. Checks on the loaded files do not, on their own, prove that no later network request occurs.

## A shared shape, and a mute

The demonstration on this page shows the 435 parameters as points in a sphere, using a fixed encoding so that different authored sets can later be compared under the same picture.

<PongArtifact />

Each parameter has a fixed direction, and its value moves the point along that ray. The directions and scale stay the same for every set. The mapping compresses large magnitudes, so two points that sit close together are not necessarily close in value, and the shape is not a score. It is not a picture of a brain, or of meaning, or of intelligence. Reordering the hidden units can change the shape without changing how the network behaves.

The demonstration includes a control to mute one hidden unit and show the three action scores immediately. That shows whether those outgoing connections change the scores at the current state. A different score does not necessarily change which action wins. A mute that does nothing is still a result: the unit may be inactive at that state. The page can also run the original and the muted copy forward together from the same point in play, so a change can be watched rather than inferred from one state alone.

## What is in place, and what is still open

The demonstration uses demonstration weights only. Those numbers were not written by a language model, and they are not a contestant artefact. No model-written player has been requested or evaluated yet.

We plan to ask one identified Grok model for a single initial list of 435 numbers, with no revisions. The exact model identity is still pending confirmation. If that list is accepted, it would be played in 32 scheduled games against four fixed baselines, on four public serves, with the candidate on each side in turn. Those 32 games are a schedule, not a result, and they have not been run. They could describe how one initial attempt plays against those baselines. They cannot show improvement from revision, success across many attempts, or a ranking of models, and they are not a held-out generalisation test.

Until that attempt exists, we cannot say whether Grok can write a working player, how it will produce the weights, or how much of the game it needs to be shown. The page is there to make those questions inspectable. It does not yet answer them.
